# /flow — 한 번에 테스트 푸시까지

흐름 전체: `docs/08-AI워크플로우/00-START-HERE.md`. 단계별 절차는 `flow-ticket` → `flow-plan` → `flow-impl` → `flow-ship` 의 SKILL.md 를 **순서대로 읽고 따른다.** 이 파일은 그 절차에서 **바뀌는 점만** 적는다.

입력: $ARGUMENTS

## 멈추는 곳 — 이 두 곳뿐
1. **앞쪽 질문 1회(있을 때만)** — 티켓의 `확인 필요:` · 그래프의 Q-표 · 운영 Worker/DB 배포 승인(그래프 배포 영향에 Worker·DB 가 있을 때)을 **계획을 다 쓴 뒤 한 번에 모아** 묻는다(AskUserQuestion, 권고안 먼저). 물을 게 없으면 묻지 않는다. 답을 받으면 같은 턴에 끝까지 간다.
2. **실기기 확인** — 테스트 푸시 뒤 링크·확인 목록을 보여 주고 멈춘다. 다음은 `/flow-submit #N`. **앱 번들이 없는 변경(Worker·DB 만)** 은 실기기 대신 `wrangler deploy` 뒤 **다음 Cron 결과 확인**(`collect_run` 조회 기준·시각을 적어 두고)에서 멈추고, 검수요청(5단계)은 없다 — 확인되면 `/flow-close #N`.

그 밖의 단계 끝 보고·"다음 단계는 …" 확인·`/clear` 권유는 하지 않고 바로 다음 단계로 간다. 실패·3회 재시도·그래프 밖의 일이 생기면 그때만 멈추고 보고한다.

## 작은 변경 — 노드 1개 · Q 0개 · DB 없음
- **계획 문서 축약형**: 첫머리(대상 이슈·배포 영향·상태) + §1 사실 표 + 노드 표 + T-id 표만. 경로·환경 전제·교차검증 초점·문서 최신화 절은 쓰지 않는다. 계획 문서는 **N1 커밋에 같이 넣는다**(따로 커밋하지 않는다).
- **검증**: `npm test && npm run typecheck` + T-id 🔴 변이 1회. W-id 는 화면 노드일 때만 1회 확인하고 W 변이는 하지 않는다. `/code-review` 는 `low`.
- **이슈**: 라벨은 등록 때 `stage:ticket`, 테스트 푸시 뒤 `stage:testing` 두 번만 붙인다. 댓글은 테스트 푸시 뒤 1번(계획 경로 · 커밋 · 배포 기록 · 실기기 확인 목록을 한데).
- **문서 커밋**: N1(코드+계획) → 배포 기록 1개. 그 사이 상태 줄 커밋은 하지 않는다.

큰 변경(노드 2개 이상·Q 있음·DB/Worker)은 각 SKILL.md 를 그대로 따르고 위 「멈추는 곳」만 적용한다.
