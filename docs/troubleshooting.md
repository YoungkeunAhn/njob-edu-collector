# 트러블슈팅

운영하면서 실제로 겪은 문제와 원인 분석입니다. 괄호 안 커밋 해시는 비공개 운영 저장소 기준이고, 코드와 테스트는 이 저장소에서 바로 볼 수 있습니다.

## 1. 3개 소스가 엣지에서만 실패 — 로그에 원인을 남기는 것부터

- **상황**: 로컬에서는 되는데 Cron에서만 실패하는 소스가 생겼습니다. 오류에는 `HTTP 403 host`만 남아 누가 막았는지 알 수 없었습니다.
- **진단**: 오류 기록에 응답의 `server` 헤더와 본문 앞 120자를 추가했습니다([HTTP 오류 메시지](../worker/src/sources/util.ts#L28), 5d9ecfb). 다음 Cron에서 원인이 갈렸습니다.
  - 주변애: 엣지 fetch와 Browser Rendering 모두 403, 로컬 curl은 200
  - 잡아바: 웹방화벽 HTML이 내려와 JSON 파싱 실패
  - 더팀스: `server=cloudflare`, "Just a moment..." 봇 차단 페이지
- **해결**: 먼저 차단이 확인된 소스를 수집 목록에서 내렸습니다(`enabled=false`). 빠지는 강좌가 많아(더팀스만 200여 건) 어댑터를 되살려 로컬 수집 목록(`LOCAL`)으로 분리하고, Windows 작업 스케줄러가 매일 03:30에 같은 코드를 돌립니다([`worker/scripts/collect-local.ts`](../worker/scripts/collect-local.ts)). 엣지에서 차단되는 소스를 우회하지 않고 실행 위치만 바꿨습니다.
- **결과**: 10.22 첫 로컬 수집 1,097건(노출 217건), 이후 매일 세 소스 모두 성공 기록.

```
2026-10-22T18:32:15.676Z jobaba: OK 받음 10 · 저장 10 · 정규화 실패 0
2026-10-22T18:32:15.687Z greenlove: OK 받음 11 · 저장 5 · 정규화 실패 0
2026-10-22T18:32:15.687Z theteams: OK 받음 1093 · 저장 1093 · 정규화 실패 0
```

## 2. 헤드리스 수집이 엣지에서 60초를 넘겼다

- **상황**: AI디지털배움터는 JS로 목록을 그리는 사이트라 Playwright(Cloudflare Browser Rendering)로 수집합니다. 엣지에서 페이지 열기가 타임아웃났습니다.
- **진단**: `wrangler dev --remote`로 엣지에서 재현해 대기 조건별로 쟀습니다. 페이지가 계속 요청을 보내 `networkidle` 62.8초, `load` 62.7초였고, `domcontentloaded`는 4.0~4.4초였습니다.
- **해결** ([`worker/src/sources/digital-baeum.ts`](../worker/src/sources/digital-baeum.ts), 67f386c · 9bbac34)
  - `domcontentloaded` 뒤에 목록을 불러오는 사이트 함수(`FnAjax_DivMethodPost`)가 준비될 때까지만 기다림
  - 페이지를 넘기는 사이 총건수가 바뀌면(5,335 → 5,334) 처음부터 1회만 다시 받음
  - 운영 Cron에서 첫 열기가 30초를 넘긴 날이 있어 열기만 1회 재시도, 전체 9분 예산
- **결과**: 엣지 재현 환경에서 실제 어댑터로 5,338건을 81초에 받았습니다. `networkidle`로 되돌리거나 재시도를 없애면 실패하는 것을 테스트로 확인했습니다.

## 3. 부분 실패가 데이터를 지우지 않게

- **상황 1**: 같은 `source_id`가 한 배치에 두 번 오면 PostgreSQL이 upsert를 거부해 소스 전체가 실패했습니다.
- **상황 2**: 대구 소스는 깨진 링크("기관명@" 등) 9건이 정규화 실패로 잡혀, 정리가 매일 건너뛰어졌습니다.
- **해결**: 배치 안에서 마지막 행만 남기도록 중복을 먼저 제거했습니다([`runSource`](../worker/src/collect/run.ts#L62-L75)). 깨진 링크는 기관 포털 링크로 바꿔 정규화 실패를 9건에서 0건으로 줄였습니다(134e890).
- **정리 가드** ([`run.ts`](../worker/src/collect/run.ts#L77-L84) · [`rules.ts`](../worker/src/core/rules.ts#L25) · [`collectPages`](../worker/src/sources/util.ts#L44-L74)): 페이지 미완결, upsert 실패, 직전 성공 대비 50% 미만, 정규화 실패 중 하나라도 있으면 삭제하지 않습니다. upsert가 중간에 실패하면 실패로 기록해 다음 급감 비교의 기준에서도 뺍니다. 가드 조건을 하나씩 지워 테스트가 실패하는지 확인했습니다(변이 확인, 9f0af10).
- **DB 쪽 방어**: 트리거가 `last_seen_at`을 과거로 돌리지 않고, 사람이 고친 분류(`category_by='manual'`)를 수집이 덮어쓰지 않게 막습니다([`course_triggers.sql`](../supabase/migrations/20261011000003_course_triggers.sql)).

## 4. Cron 실행 시간

- **상황**: 고용24 실사이트 드라이런이 전체 591초 걸렸습니다. 같은 Cron 그룹의 다른 소스까지 그만큼 늦게 끝나는 구조였습니다.
- **해결**: "그룹이 한도를 넘으면 시각을 나눠 쪼갠다"는 규칙대로 고용24를 A1(03:00)으로 떼고 나머지 API 3개를 A2(03:10)로 옮겼습니다(30faabb). 이와 별도로 Worker CPU 한도(`cpu_ms`)를 300초로 설정했는데, 배포 오류(code 100328)로 유료 플랜이 필요하다는 것을 확인해 전환했습니다.
- **결과**: 고용24와 나머지 API 소스를 서로 다른 Cron 실행으로 분리했습니다. 실패 알림은 그룹 단위로 한 번만 보냅니다.
